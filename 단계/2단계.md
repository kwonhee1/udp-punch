# 2단계: 같은 브라우저 처리 추가

## 목적

- 같은 브라우저(같은 공유기)에서 연 두 페이지끼리도 연결되게 한다.
- 1단계는 host 후보를 지우고 srflx로만 연결하므로, 공유기가 헤어핀 NAT를 지원하지 않으면 같은 네트워크끼리는 연결되지 않았다.

## 방식

- [연결]을 누른 쪽이 상대의 공인 IP와 내 공인 IP를 비교한다.

| 비교 결과 | 보내는 후보 | 예상 경로 |
|---|---|---|
| 같음 | host 후보 유지 (host + srflx) | host ↔ host |
| 다름 | srflx만 (1단계와 같음) | srflx ↔ srflx |

- 공인 IP: 페이지를 열 때 STUN으로 받은 srflx 주소 (IPv4 우선). 로비(presence)에 이름·기기와 함께 올린다.
- 판단은 [연결]을 누른 쪽만 한다. offer에 `local: true`를 같이 보내고, 받는 쪽은 그 값대로 answer를 만든다.

## 파일

- `web/standalone-2.html`: 1단계 `web/standalone.html`을 복사해 아래만 바꿨다.
  - `Punch.createOffer(keepHost)`, `createAnswer(sdp, keepHost)`, `localSdp(keepHost)`: keepHost면 host 후보를 지우지 않는다.
  - `connectTo`: `peer.ip === me.ip`이면 offer에 `local: true`
  - `handleSignal`: 받은 offer의 `local` 값을 따른다.
- 배포: `http://test-udp.kro.kr`

## 결과

**성공** (2026-11-09)

| 환경 | 결과 |
|---|---|
| 로컬, 같은 Chrome 두 탭 | `host :62324 ↔ host :53290`, 왕복 1.3ms |
| 배포 주소 `http://test-udp.kro.kr` | 성공 (사용자 확인) |

- 1단계 코드로는 같은 브라우저 두 탭이 연결되지 않던 경우다 (헤어핀 NAT 미지원).

## 남은 확인

- 같은 경우 받는 쪽 answer에 host 후보만 들어가고 srflx가 빠진 적이 있다. 같은 통신사 휴대폰 두 대처럼 공인 IP만 같고 실제 네트워크가 다르면 연결이 안 될 수 있다.
- Safari는 카메라·마이크 권한이 없으면 host 후보를 주지 않을 수 있다.
