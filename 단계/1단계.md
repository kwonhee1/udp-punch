# 1단계: UDP 홀 펀칭 성공

## 목적

- Backend 없이 두 브라우저를 공인 주소(srflx)끼리 WebRTC DataChannel로 직접 연결한다.
- 방, 사용자 이름, 기기 찾기, 파일 전송은 다루지 않는다.

## 구성

- 공인 주소 확인: 외부 공개 STUN (`stun:stun.l.google.com:19302`)
- 시그널링: Supabase (PostgreSQL), 고정 행 하나 (한 번에 한 쌍만 연결)
- 변경 감지: Supabase Realtime (`postgres_changes`)
- 프론트: Vanilla JS, 빌드 없음

## 시그널링 방식

- ICE 후보 수집이 끝날 때까지 기다린 뒤, 후보가 모두 담긴 SDP를 한 번에 쓴다 (trickle ICE 사용 안 함).
- SDP에서 `typ host` 후보 줄을 지우고 쓴다. 사설 주소 경로를 막아 공인 주소로만 연결되게 한다.

## DB 구조

```sql
create table signal (
  id         int primary key default 1 check (id = 1),  -- 행은 항상 하나
  offer      text,                                      -- A의 { sid, sdp } JSON
  answer     text,                                      -- B의 { sid, sdp } JSON (sid는 offer와 같음)
  updated_at timestamptz not null default now()
);

-- Realtime 변경 감지 대상에 추가
alter publication supabase_realtime add table signal;

-- 테스트 기간 동안 익명 사용자 읽기·쓰기 허용
grant select, insert, update, delete on public.signal to anon;
alter table signal enable row level security;
create policy "anon all" on signal for all to anon using (true) with check (true);
```

- A는 [연결]을 누를 때 `id = 1` 행을 `offer = 새 SDP, answer = null`로 덮어쓴다 (upsert).
- srflx 후보(공인 IP:포트)는 SDP 안에 들어 있다.

## 동작 흐름

1. B: 페이지를 열면 `signal` 행을 한 번 읽고, 이후 변경을 구독한다.
2. A: [연결] 클릭 → DataChannel 생성 → offer 생성 → 후보 수집 완료 대기 → host 후보 제거 → `offer` 쓰기, `answer` 비우기
3. B: `offer`가 있고 `answer`가 비어 있으면 → answer 생성 → 후보 수집 완료 대기 → host 후보 제거 → `answer` 쓰기
4. A: `answer` 변경을 받아 적용한다.
5. 양쪽: ICE 연결 확인(홀 펀칭) → DataChannel open
6. A가 ping을 보내고 B가 pong으로 답한다.
7. 양쪽: getStats로 선택된 후보 쌍을 조회해 표시한다.

## 완료 기준

- 서로 다른 네트워크(예: PC Wi-Fi ↔ 휴대폰 모바일 데이터)의 두 기기가 연결된다.
- 선택된 후보 쌍이 양쪽 모두 srflx(또는 prflx)다.
- ping / pong이 오간다.

## 테스트

| 순서 | 환경 | 기대 결과 |
|---|---|---|
| 1 | PC 두 탭 (localhost) | 공유기가 헤어핀 NAT를 지원하면 성공, 아니면 실패 (둘 다 정상) |
| 2 | PC Wi-Fi ↔ 휴대폰 모바일 데이터 | 성공 (완료 기준) |

- 휴대폰은 HTTPS가 필요하므로 임시 터널(cloudflared 등)로 접속한다.
- 모바일 통신망이 대칭형 NAT이면 실패할 수 있다. 이 경우 다른 통신사나 핫스팟으로 다시 확인한다.

## 결과

**성공** (2026-11-09)

- 1단계 결과물은 단일 HTML `web/standalone.html`이다. 이 문서 앞부분(구성, DB 구조, 동작 흐름, 파일 구조)은 이전 `signal` 테이블 방식 기준이고, 정리는 프로젝트 생성 단계에서 한다.
- 테스트 파일: `web/standalone.html`, 배포 주소 `http://test-udp.kro.kr`
  - 시그널링은 `signal` 테이블 대신 Supabase Realtime 채널 `lobby`를 쓴다. presence로 접속 기기 목록을 보여 주고, broadcast로 offer·answer를 상대에게만 보낸다.
  - 화면: 내 기기·공인 주소, 접속 중인 기기 목록, 기기별 [연결] / [핑] 버튼
- 환경: PC Wi-Fi ↔ 휴대폰 모바일 데이터

| 항목 | 결과 |
|---|---|
| 선택된 후보 쌍 | `srflx 223.194.166.249:51665 ↔ srflx 117.111.7.54:34891` |
| ping / pong | 양방향 성공, 왕복 40.5ms (이후 138.7ms) |
| 연결까지 걸린 시간 | offer 전송 후 약 1초 |

- 같은 날 이전 버전(`signal` 테이블 방식)으로도 성공했다: `srflx 117.111.7.86:50513 ↔ srflx 210.124.243.90:63201`, 왕복 44.5ms
- 같은 테스트에서 다른 기기 하나(초록 펭귄)는 ICE `checking` 후 `disconnected`로 실패했다. 상대 기기의 IP는 기록하지 않아서 원인을 확인하지 못했다. 가능한 원인은 같은 공유기에서 헤어핀 NAT를 지원하지 않는 경우, 또는 대칭형 NAT다.
- PC 쪽 NAT는 내부 포트를 그대로 유지했다 (host `:51665` → srflx `:51665`).
