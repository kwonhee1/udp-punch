# 브라우저 P2P 파일 전송 요구사항

> 시스템 구성과 기능별 상세 요구사항은 [기능명세.md](기능명세.md) 참고.

## 단계 명세

1~5단계는 Backend 서버 없이 진행한다. 시그널링은 외부 DB, 공인 주소 확인은 외부 공개 STUN 서버를 사용한다.

```
[외부 DB] ← 시그널링(SDP·ICE) → [기기 A 브라우저] ═══ DataChannel (UDP) ═══ [기기 B 브라우저]
                                        │                                  │
                                        └────── 외부 공개 STUN 서버 ─────────┘
```

### 1단계: UDP 홀 펀칭 성공

- **상태**: 완료 (2026-11-09, 결과는 [1단계.md](1단계.md#결과) 참고)
- **목표**: Backend 없이 두 브라우저를 WebRTC DataChannel로 직접 연결한다.
- **구성**
  - 공인 주소 확인: 외부 공개 STUN 서버
  - 시그널링: 외부 DB에 SDP·ICE 후보를 쓰고 읽는다.
- **완료 기준**
  - 두 기기가 DataChannel로 메시지를 주고받는다.
  - 선택된 후보 쌍이 `srflx`(STUN으로 얻은 바깥 주소)임을 확인한다. 같은 공유기 아래에서는 `host` 후보로 바로 붙어 홀 펀칭이 일어나지 않으므로, 서로 다른 네트워크(예: Wi-Fi와 모바일 데이터)에서 확인한다.
- **상세**: [단계/1단계.md](단계/1단계.md)

### 2단계: 같은 브라우저 처리 추가

- **상태**: 완료 (2026-11-09, 결과는 [2단계.md](2단계.md#결과) 참고)
- **목표**: 같은 브라우저에서 연 두 페이지끼리도 연결되게 한다.
- **배경**: 1단계는 host 후보를 지우고 srflx로만 연결한다. 같은 기기·같은 공유기 아래에서는 공유기가 헤어핀 NAT를 지원하지 않으면 연결되지 않는다.
- **방식**: [연결]을 눌렀을 때 상대의 공인 IP가 내 공인 IP와 같으면 host 후보를 남긴다. 다르면 1단계처럼 srflx만 보낸다.
- **완료 기준**
  - 같은 브라우저의 두 탭이 DataChannel로 메시지를 주고받는다.
  - 서로 다른 네트워크 간 연결(1단계)은 그대로 srflx로 된다.

### 3단계: 프로젝트화

- **목표**: 단일 HTML(`web/standalone.html`)을 프로젝트 구조로 옮겨 HTTPS 주소에 올릴 수 있게 한다.
- **배경**: 지금 쓰는 도메인 단일페이지 기능은 HTTP만 제공한다. HTTPS를 붙이려면 빌드·배포가 가능한 프로젝트가 필요하다.
- **완료 기준**
  - 프로젝트 빌드 결과를 HTTPS 주소로 접속해 1·2단계와 같은 연결이 된다.
- **확정 필요**
  - 프레임워크 (React 등)
  - 빌드 도구
  - HTTPS를 지원하는 호스팅

### 4단계: 프론트 홀 펀칭 코드 라이브러리화

- **목표**: 1단계 코드를 다른 화면·서비스에서 가져다 쓸 수 있는 라이브러리로 정리한다.
- **완료 기준**
  - 연결 생성, 메시지 송수신, 연결 상태 변경을 라이브러리 API로 사용할 수 있다.
  - 1단계 연결 테스트를 라이브러리 API로 다시 작성해도 동작한다.
- **확정 필요**
  - 라이브러리 API 형태
  - 시그널링 수단(외부 DB)을 교체할 수 있게 분리할지 여부

### 5단계: 서비스 올리기

- **목표**: 프론트를 정적 호스팅에 배포해 외부에서 접속할 수 있게 한다.
- **구성**: 정적 파일 배포만 한다 (Backend 없음).
- **완료 기준**
  - HTTPS 주소로 접속해 1단계와 같은 연결이 된다.
- **확정 필요**
  - 정적 호스팅 서비스 (GitHub Pages, Cloudflare Pages, Vercel 등)
  - 외부 DB 키를 프론트에 넣을 때의 접근 규칙
